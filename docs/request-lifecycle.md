# Request lifecycle and cleanup

R6 gives the server request task sole responsibility for backend cleanup. `session::run_streaming` receives input and sends regular data; it neither closes the backend nor sends terminal success. The task awaits `backend.close()` exactly once, outside the RPC deadline/cancellation wrapper, before finalizing its result. Its execution permit remains owned until cleanup and finalization finish. Dropping a response or expiring its deadline cannot release the worker's permit while close is pending.

After successful streaming and cleanup, terminal `Event` and `SUCCESS` keep their existing wire order. Their sends still obey RPC deadline, output timeout, response closure and shutdown. A deadline that expires during cleanup suppresses success after cleanup finishes. When streaming and cleanup both fail, the streaming error remains the returned cause and `cleanup_failed` remains available in diagnostics.

The client now keeps request queues and lifecycle fields private in `client/state.rs`. Input phase, backend outcome, cleanup acknowledgement, terminal consumption, registration and processing notification are separate enums. Core, endpoint and driver code call transition methods rather than mutating these fields. Transitions return owned discarded buffers and retirement/notification effects; the request releases leases and calls registry/waker operations after dropping its state lock.

`ProcessingFinished` is still an optional processing notification, not a cleanup or success acknowledgement. `closed()` acknowledges cleanup independently of output consumption and its result cannot be overwritten by later delivery deadlines. Successful queues drain before `Completed`, followed by `None`; an error bypasses queued data once, followed by `None`. Dropping `Closed` or `Shutdown` waiters leaves their owner tasks alive. Control-only drop does not cancel a request.

Validation covers client cancellation/completion races, output deadlines after cleanup, pending buffer budgets, multiple waiters and reentrant wakers. Added server gates exercise deadline, cancellation and response drop during close; failure tests check error priority and suppression of success. A client test drops both cleanup waiters while retaining the worker/shutdown owners. Server protocol tests retain the normal wire contract. No queue capacities, model reuse policy or guarantee after Tokio runtime destruction is changed.
